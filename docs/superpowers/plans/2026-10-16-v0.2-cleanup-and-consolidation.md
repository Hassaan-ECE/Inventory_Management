# Inventory Management 0.2 — cleanup and consolidation

Date: 2026-10-16
Branch: `feature/0.2-cleanup` (from `main` at 0.1.4, `714a136`)
Status: **All phases done (marker pruning deliberately deferred). The signed 0.2.0 installer is built and verified; publishing waits for the owner (see Phase 6).**

## Goal

Ship 0.2.0 with the same features, less code, one storage layer, one sync engine, safe developer builds, and a test share that exercises every field combination. Nothing changes for users except the sync warning, the EVCS Storage/ME Storage menu, and a one-time local database merge.

## Hard constraints

- **0.1.4 clients must keep syncing during rollout.** 0.2 writes the same S: op, snapshot, and manifest formats into the same folders (TE schema v2, Storage schema v1, Lab catalog v2). Format changes wait for a later release, after everyone is on 0.2.
- **S: stays one stream per inventory.** A single database file on S: is not safe for several writers, and separate streams mean one inventory's problem can't stall the others.
- **No data loss on the local merge.** Old local files are kept as backups, counts and pending outbox ops are checked before switching, and failure leaves the old files in use.
- Every phase ends green: Rust tests, Clippy `-D warnings`, rustfmt, frontend lint, tests, and build.

Order: 1 → 3 → 4 (with the sync warning built once into the unified engine) → 2 → 5 → 6. The warning and the dev share both need the sync engine, so they come after it is unified instead of being written three times.

## Phase 1 — Developer safety (done 2026-10-16)

1. **Dev builds never touch live data.** Debug builds (`cfg!(debug_assertions)`) default to `.tmp/dev-data` for local databases and `.tmp/dev-share/modules/<folder>` for each shared root (`backend/src/platform/dev_build.rs`). The env overrides still win. Verified with `bun run dev:desktop`: databases created in `.tmp/dev-data`; no S: or `%LOCALAPPDATA%` writes.
2. **DEV badge.** One shared `StatusFooter` (`frontend/src/platform/ui/StatusFooter.tsx`) replaces the three copied footers; in dev builds its corner shows `DEV build` instead of the author credit.

## Sync warning (built in Phase 4, `11546e1`)

When a module is skipping remote files, the footer shows a warning that stays visible until the problem clears. Files from a newer app version are reported as "update required", not as corrupt. Implemented once in the unified engine as a structured `warning` on the shared status (not text appended to the message, which the 0.1.4 update message overwrites).

## Phase 2 — Developer test share (done 2026-10-19)

Built as `backend/src/dev_share/` and `bun run dev:share`. Alice, Bob, and Carol (three fake computers, each with one 0.2 database) write the fixtures through the real mutations and sync engines and sync until they agree; each starts a different inventory, so every share has a snapshot plus later operations from other clients. Tests: a fresh computer syncs every fixture and lands on the expected merged results; the share holds manifests, snapshots, and later operations; every synced field (TE and EVCS Storage `ENTRY_FIELDS`, every Lab entity field except the 0.1 `legacy` block) is set by some fixture; rebuilding never clears a non-dev folder; the live share and its parents are refused. The previous `.tmp/dev-data` moves to `.tmp/dev-data-previous` on each default rebuild.

Original scope:

- **Rule:** every new field or feature adds fixtures in the same change.

## Phase 4 — One local database, one sync engine, backend restructure

- One `inventory-management.feox` per PC, keys namespaced per inventory; a one-time startup merge from the three current files. **Done (4a):** `platform/database.rs` (`LocalDatabase`, `Namespace`) and `platform/legacy_databases.rs`. The merge copies into a staging file, verifies every key against its source after reopening the staging file from disk, renames it into place, and moves the old files to `pre-0.2-databases\`. Rehearsed on copies of the owner's live databases on 2026-10-16: TE 3,359, Lab 334, EVCS 802 keys, all matched, 4.7 s.
- **FeOx capacity (found 2026-10-16).** FeOx files are fixed-size and every record uses at least one 4 KiB block. When the file is full, inserts still succeed in memory, but the background disk write fails silently, so the data is lost on restart. The 64 MiB 0.1.x files held about 16,000 records; the live TE file is at 3,359 (about 20%), and grows by two markers (`sync:applied`, `sync:seq`) per synced op, forever. The merged file is 256 MiB (about 65,000 records, roughly 14x current use). Still to do in Phase 4:
  - **Done:** a capacity check that shows a footer warning at 80% or more (part of the footer sync warning, `11546e1`). FeOx's `write_failures` counter is also surfaced, as "Changes not saving".
  - **Deferred, on purpose:** pruning `sync:applied` / `sync:seq` (and the never-deleted `sync:outbox` records). Applied markers are what stop an operation from being applied twice. If a snapshot ever lowers the watermarks, a pruned TE operation could be re-merged onto newer data through the disjoint-field rule. Do it later as its own change, with a proof that every path that rescans ops below a watermark is covered. 256 MiB is about 14x current use, and the footer now warns long before it fills.
- One storage wrapper and one inventory-entry sync engine, generic over the record type. TE and EVCS Storage plug in; Lab catalog sync moves onto the same file/lock/snapshot helpers.
  - **Done (4b, 2026-10-16):**
    - The path-included integration test crates moved inside the crate (`9410b21`).
    - The Lab v1 model, sync copy, migration, and cutover are removed (`7aedd96`); a brand-new Lab shared root is set up by the first sync.
    - `platform/store` (`ModuleStore<R>`) replaces the three storage copies.
    - `platform/sync` is the one entry engine. TE and EVCS Storage implement `SyncRecord`, and `MergeRule::{DisjointFieldsFromSameBase, PerFieldVersions}` keeps each 0.1.4 rule.
    - Entry states serialize exactly as 0.1.4 did per inventory: TE omits `fieldVersions`/`recoveryEntry`. This matters because snapshot checksums are verified by re-serializing, so an extra field would make 0.1.4 reject 0.2 snapshots. Tests pin both field sets.
    - EVCS Storage's local-only improvements now apply to both inventories: bootstrap skips entries that already have sync state, and the default module folder is created when `modules\` exists.
  - **Cross-version check (2026-10-16):** the pre-engine commit and the new engine exchanged TE and EVCS Storage operation files and snapshots through a temporary shared root, in both directions, with zero corrupt files and each side applying the other's snapshot. Repeat it in Phase 6 against an installed 0.1.4.
  - Lab catalog sync onto the shared file/lock/snapshot helpers moves to Phase 5, together with splitting `catalog_sync.rs` (the same file).
- The backend layout matches the frontend:
  - `platform/` holds the database, sync engine, paths, and runtime;
  - `modules/<inventory>/` holds the model, commands, queries, mutations, and export;
  - TE moves out of the top level into `modules/te_test_equipment/`.
- The divergence and restore tests from 0.1.4 must pass unchanged in meaning.
- **Merge rules stay per inventory.** TE merges concurrent edits to different fields only when both started from the same base version; EVCS Storage keeps a version per field and takes the newest per field. The shared engine takes the record type *and* its merge rule as plug-ins, and each rule is bit-for-bit the 0.1.4 behaviour. If a 0.2 PC and a 0.1.4 PC resolved the same ops differently, the team would drift apart again. Unifying the rules is a later, coordinated change.

## Phase 5 — Types and file size

**Types (done 2026-10-19).** `ts-rs` derives on every bridge payload; `cargo test` writes them to `frontend/src/integrations/tauri/generated/`. TE, Lab, and EVCS Storage `types.ts` re-export them, and the bridges call `invoke<GeneratedType>`. The hand-written guards are deleted rather than generated: the backend ships in the same build, so a payload cannot come from another version, and the legacy-data normalization they repeated already happens in Rust deserialization. Status unions the frontend needs (TE lifecycle and working status) come from `#[ts(type)]` unions that a Rust test pins to `LIFECYCLE_STATUSES` and `WORKING_STATUSES`. The unused TE backend query path and the Lab v1 bridge contract went with them.

**Files (done 2026-10-19).** Split along real seams: `catalog_sync.rs` → `catalog_sync/` (types, outbox, operation files, apply, snapshot, share, tests); `api/commands.rs` → `api/commands/` (inventory, lab_catalog, calibration_roster); `PartDialog.tsx`, `TeLabComponentsView.tsx`, and `CalibrationRosterDialog.tsx` each into a view plus focused helpers. The Lab catalog now shares the engine's file helpers (`platform/sync/files.rs`: canonical JSON, checksums, SHA-256 via `sha2`, atomic writes), root resolution, and status building; a golden test captured before the change pins the exact bytes Lab writes. The Lab catalog keeps its own snapshot policy (no lock, never compacts) because that is part of the catalog-v2 format 0.1.x reads.

Original scope:

- Generate TypeScript types and response guards from the Rust types (specta or ts-rs) in place of `bridgeGuards.ts` / `labBridgeGuards.ts`.
- Split files over ~500 lines along real seams: `catalog_sync.rs`, `api/commands.rs`, `PartDialog.tsx`, `TeLabComponentsView.tsx`, `CalibrationRosterDialog.tsx`.

## Clean code rules for this work

- One way to do each thing; no copies.
- Names say what the code does in user terms.
- Small modules with one job.
- Comments explain *why*, not *what*.
- No dead code, feature flags for removed features, or placeholders.
- Every behaviour change ships with a test that fails without it.
